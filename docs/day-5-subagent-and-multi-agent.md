# 第 5 天：Subagent 与 Multi-Agent

## 学习目标

学会先问“为什么需要多 Agent”，而不是一上来就拆角色。多 Agent 只在任务可独立审阅、可并行研究或需要角色制衡时有价值；简单任务通常单 Agent 更快、更便宜、更稳定。

## 当前实现

当问题包含“多智能体”“multi-agent”或“多角色”时，`agentService.js` 的 `runMultiAgent` 会并发执行：

1. planner：生成目标、计划和停止条件。
2. reviewer：找风险、证据缺口和是否需要继续拆分。
3. synthesis：合并两份独立结果。

每个角色都有独立 Trace Span。若本地小模型在并发请求时超时，系统会记录 fallback 来源，并输出稳定的结构化兜底结论；这本身就是可观察的失败恢复，而不是隐藏失败。

## 动手步骤

1. 发送“用多智能体设计会议纪要 Agent，重点说明成本与风险”。
2. 在工作台查看 planner、reviewer、synthesis 三类 Span 及耗时。
3. 对同一个问题用普通单 Agent 再问一次，比较总耗时、答案结构和 Trace 数量。
4. 记录何时应该回退单 Agent：任务简单、依赖强、上下文很短或成本预算紧张。

## 评估维度

- 质量：待办是否有负责人、截止时间、证据和风险项。
- 延迟：总耗时与 P95 耗时，而非只看平均值。
- 成本：角色数 × 输入输出 Token，加上工具调用费用。
- 一致性：不同角色的中间结论是否冲突，最终汇总是否遗漏。

## 验收标准

- 能在 Trace 中证明角色是独立调用而非同一段 Prompt 的标题变化。
- 能解释并发为什么会降低墙钟时间，也可能挤占本地模型资源。
- 能给出“单 Agent 优先”的实际判断条件。

## 面试口述要点

> 我把多 Agent 看成受控的任务图，不是 Agent 之间自由聊天。这个项目只并行 planner 和 reviewer，主 Agent 负责汇总；每个子角色的输入输出和耗时都在 Trace 里。收益是独立审阅和并行研究，代价是 Token、延迟、上下文传递和结论冲突。因此我会先用单 Agent，只有质量收益足以覆盖成本时才拆角色，并始终设置并发数与总预算。
